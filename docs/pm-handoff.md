# ITWINS TCM 产品与技术说明

## 1. 项目概述

ITWINS TCM 是一个面向中医健康咨询场景的智能会诊 MVP。系统围绕“问诊 + 舌象 + 面象 + 知识库增强”的思路，采集用户主诉、症状标签、补充问诊答案以及舌面、舌下、面部照片，调用多模态大模型和中医知识库，生成结构化的症状理解、中医分析、调理建议和风险提示。

## 2. 产品流程

产品流程分为信息采集、观察分析、信息校验、综合会诊和结果追问五个阶段。

用户先输入当前最主要的不适，例如失眠、胃胀、疲惫、口干等，并选择相关症状标签。系统根据主诉、症状和场景生成补充问诊问题，用于补齐病程、睡眠、饮食、消化、寒热感受、情绪状态等关键线索。

用户回答补充问题后，可以上传舌面、舌下和面部照片。系统先判断图片是否可用于观察，再分别提取舌象和面象线索，包括舌质颜色、舌苔、齿痕、裂纹、润燥、舌下络脉、面色、光泽、唇色、眼周状态等。

在生成结果前，系统会检查用户自述信息是否存在明显前后矛盾。例如症状标签选择“怕冷”，补充问诊又回答“明显怕热”时，系统会先请用户确认，避免基于冲突信息生成会诊结果。

最终，系统结合问诊信息、舌象观察、面象观察和中医知识库，生成四类结果：症状理解、中医分析、调理建议、风险提示。用户查看结果后，可以围绕结果继续追问，例如“我应该怎么调整作息”“这个建议适合我吗”“什么情况需要去医院”。

整体流程如下：

```text
主诉与症状 -> 补充问诊 -> 舌象/面象上传 -> 信息一致性检查 -> 综合会诊结果 -> 继续追问
```

## 3. 技术路线

以下按一次完整会诊的执行顺序说明技术实现。前端负责收集文本和图片信息，后端按任务拆分为多个 API；文本类 API 调用 `qwenModel`，视觉与多模态类 API 调用 `qwenVisionModel`；模型输出经 JSON 解析、卡片解析和术语清洗后，返回前端展示。

### 3.1 页面初始化

- 触发点：用户打开 `https://itwins-tcm.vercel.app`
- 前端入口：`src/app/page.tsx`
- 主页面组件：`src/features/tcm/TcmConsultationPage.tsx`
- 技术：Next.js 16 App Router、React、TypeScript、Tailwind CSS 4
- 作用：
  - 渲染主诉输入、症状标签、舌象上传、面象上传、结果卡片、追问聊天等界面
  - 在浏览器里维护用户填写状态
  - 根据不同阶段调用后端 API
- 输出：用户看到可交互的中医会诊页面

### 3.2 用户提交主诉，生成补充问诊

该步骤的目标是把用户的简短主诉转化为可继续分析的问诊信息。系统不会直接给出结论，而是先让模型根据主诉、症状标签和场景生成 4 到 6 个补充问题，覆盖病程、睡眠、饮食、消化、寒热、情绪等与当前主诉相关的关键维度。

- 用户输入：
  - 主诉，例如“最近入睡困难、容易疲惫”
  - 已选症状标签
  - 可选主题，例如睡眠、脾胃、情绪等
- 前端调用：
  - `src/services/tcmConsult.ts`
  - `startConsultation()`
- 后端 API：
  - `POST /api/tcm/start`
  - 文件：`src/app/api/tcm/start/route.ts`
- 后端处理：
  - 使用 `buildStartUserPrompt()` 把主诉组装成用户提示词
  - 使用 `TCM_START_SYSTEM_PROMPT` 约束模型只生成补充问诊问题
  - 通过 `getQwenClient()` 调用 DMXAPI
- 模型与技术：
  - 模型服务：DMXAPI
  - 模型：`DMX_TEXT_MODEL=qwen3-vl-plus`
  - API 协议：OpenAI-compatible Chat Completions
  - 客户端封装：`src/services/qwenClient.ts`
- 输出：
  - 结构化补充问诊问题数组
  - 每个问题包含问题文案、选项、单选/多选规则、是否允许“其他”
- 价值：
  - 将简短主诉扩展为更完整的问诊信息
  - 提升后续分析所需上下文的完整性和针对性

### 3.3 用户回答补充问诊并上传图片

该步骤负责把用户补充问诊答案和图片材料整理为后端可处理的输入。图片会在浏览器端先做类型、大小和尺寸处理，降低用户上传超大原图导致接口超时的风险。

- 用户输入：
  - 补充问诊答案
  - 舌面照片
  - 舌下照片
  - 面部照片
- 前端图片处理：
  - 文件：`src/services/imageValidation.ts`
  - 调用位置：`src/services/tongueAnalysis.ts`、`src/services/faceAnalysis.ts`
  - 技术：浏览器端图片格式校验、8MB 大小校验、最长边压缩到 1200px、转为 JPEG
- 作用：
  - 避免用户上传非图片或过大的图片
  - 在上传前压缩图片，降低 Vercel API 请求体积和超时风险
- 输出：
  - 可发送给后端的压缩图片数据
  - 舌面、舌下、面象三个图片输入继续参与后续分析

### 3.4 舌象分析

舌象分析采用“结构化文字指令 + 图片”的多模态方式。后端会明确告诉模型两张图片的顺序和用途：第一张用于观察舌质、舌苔、齿痕、裂纹和润燥，第二张用于观察舌下络脉。模型必须按固定 JSON 字段返回结果，便于前端展示和后续综合分析复用。

- 前端调用：
  - `src/services/tongueAnalysis.ts`
  - `analyzeTongueImages({ top, underside })`
- 后端 API：
  - `POST /api/tcm/tongue`
  - 文件：`src/app/api/tcm/tongue/route.ts`
- 后端输入：
  - 舌面图片
  - 舌下图片
- 后端处理：
  - 再次校验上传图片格式和大小
  - 把图片转成 data URL
  - 把结构化文本指令、舌面图片、舌下图片一起传给视觉模型
  - 要求模型返回固定 JSON 字段
  - 使用 JSON 解析工具校验和提取结构化结果
- 模型与技术：
  - 模型服务：DMXAPI
  - 视觉模型：`DMX_VISION_MODEL=qwen3-vl-plus`
  - 多模态输入：结构化文本指令 + 舌面图片 + 舌下图片
  - JSON 解析：`src/services/jsonResponse.ts`
- 输出字段示例：
  - `tongueBodyColor`：舌体颜色
  - `tongueCoatColor`：舌苔颜色
  - `tongueCoatThickness`：舌苔厚薄
  - `tongueShape`：舌体形态
  - `teethMarks`：齿痕
  - `cracks`：裂纹
  - `moisture`：润燥
  - `sublingualVessels`：舌下络脉观察
- 价值：
  - 舌象是中医视觉信息的重要来源
  - 结构化输出会作为 `observation.tongue` 进入最终综合会诊分析

### 3.5 面象分析

面象分析同样采用“结构化文字指令 + 图片”的多模态方式。后端会要求模型只做面象观察和图片质量判断，不做身份识别、年龄性别判断或疾病诊断。模型输出会被约束为固定字段，包括整体面色、光泽、局部色泽、眼周、唇色和神态线索。

- 前端调用：
  - `src/services/faceAnalysis.ts`
  - `analyzeFaceImage(file)`
- 后端 API：
  - `POST /api/tcm/face`
  - 文件：`src/app/api/tcm/face/route.ts`
- 后端输入：
  - 面部照片
- 后端处理：
  - 再次校验上传图片格式和大小
  - 把图片转成 data URL
  - 把结构化文本指令和面部图片一起传给视觉模型
  - 要求模型观察面色、光泽、局部色泽、眼周、唇色和神态线索
  - 解析成固定结构
- 模型与技术：
  - 模型服务：DMXAPI
  - 视觉模型：`DMX_VISION_MODEL=qwen3-vl-plus`
  - 多模态输入：结构化文本指令 + 面部图片
- 输出：
  - `complexion`：整体面色观察
  - `luster`：面部光泽观察
  - `localColor`：局部泛红、暗沉或色泽不均观察
  - `eyeArea`：眼周状态观察
  - `lipColor`：唇色观察
  - `facialExpression`：神态线索观察
  - `imageStatus`、`imageQuality`、`qualityMessage`：图片可用性和质量提示
- 价值：
  - 面象给综合会诊提供额外视觉参考
  - 结构化输出会作为 `observation.face` 进入最终综合会诊分析
  - 原始面部图片也可进入多模态综合分析链路

### 3.6 一致性检查

一致性检查是最终分析前的文本质检环节。系统只检查用户自述信息内部是否存在明显硬矛盾，不检查舌象、面象与文本之间的差异。这样可以避免因图片观察和用户主观感受不完全一致而频繁打断流程，同时仍能拦截会直接影响分析结论的文本冲突。

- 触发点：
  - 用户完成主诉、症状标签和补充问诊后
- 前端调用：
  - `src/services/tcmConsult.ts`
  - `checkConsultationConsistency()`
- 后端 API：
  - `POST /api/tcm/consistency`
  - 文件：`src/app/api/tcm/consistency/route.ts`
- 后端输入：
  - 主诉
  - 症状标签
  - 补充问诊答案
- 后端处理：
  - `buildConsistencyUserPrompt()` 只提取用户自述信息：`chiefComplaint`、`selectedSymptoms`、`selectedTopic`、`followUpAnswers`
  - 调用模型检查主诉、症状标签、补充问诊答案之间是否存在明显硬矛盾
  - 不检查舌象、面象与用户自述是否一致；这类差异留到最终分析阶段自然处理
  - 例如症状标签选择“怕冷”，但补充问诊回答“明显怕热”，才需要用户确认
- 输出：
  - `needsClarification`：是否需要再次确认
  - `issues`：最多 3 个需要用户确认的问题，每个问题包含自然中文选项
- 价值：
  - 降低用户自述前后冲突导致的分析偏差
  - 在最终会诊前做一次问诊文本质量控制

### 3.7 RAG 知识检索

RAG 的作用是把用户输入与本地中医知识库关联起来，为模型提供更具体的参考材料。当前知识库来自 SylvanL 中医数据集，已整理为 4,163 条结构化知识，覆盖症状、疾病、药膳食疗、穴位按摩等内容。系统会把主诉、症状标签和主题拼接成查询文本，再从本地 JSON 关键词倒排索引中召回相关条目，最后整理成可注入提示词的 `referenceText`。

- 触发点：
  - 用户提交最终会诊分析
- 后端位置：
  - `src/app/api/tcm/analyze/route.ts`
  - 调用 `retrieveTcmKnowledge()`
- RAG 文件：
  - `src/services/tcmRag.ts`
  - `src/services/tcmRagIndex.json`
- 知识库来源：
  - SylvanL 中医数据集
  - 当前项目已抽取并结构化为 4,163 条本地知识
  - 索引包含 84,739 个关键词入口
- 原始知识库处理：
  - 原始数据文件为 `rag/raw/CPT_tcmKnowledge_source2_12889.json`
  - 构建脚本为 `rag/buildIndex.mjs`
  - 构建时先按每条知识首行前缀识别类别，例如“症状:”“疾病:”“药膳食疗:”“穴位:”“方剂:”“中药材:”等
  - 识别后再按类别抽取结构化字段，把原始长文本拆成标题、介绍、病因、症状、主治、功效、适用人群、配方、用法、定位、操作等字段
  - 最终只把适合当前产品定位的内容写入 `src/services/tcmRagIndex.json`
- 当前保留并进入 RAG 的内容：
  - `症状`：保留介绍、主要病因、常见症状、发病部位、就诊科室、原始全文
  - `疾病`：保留介绍、主要病因、相关中医疾病、发病部位、就诊科室、原始全文
  - `药膳食疗`：保留介绍、功效、适宜人群、配方、食用方法、来源、原始全文
  - `穴位`：保留介绍、主治、功能、位置/定位、操作、隶属经络、原始全文
  - `保健品`：保留介绍、保健功能、适用人群、不适用人群、食用方法、原始全文
- 当前不进入 RAG 的内容：
  - `中药材`、`方剂`、`药名`、`术语`、`医疗美容` 在构建脚本中可以被识别，但没有写入最终 RAG 条目
  - 不使用中药材、方剂、药名，是因为当前产品定位是健康咨询和调理建议，不提供处方、用药或具体药物推荐
  - 不使用术语类内容，是因为当前会诊结果需要面向普通用户表达，术语百科对当前结果卡片帮助有限
  - 不使用医疗美容类内容，是因为它与当前中医健康会诊主流程不匹配
- 字段使用边界：
  - 用于关键词索引和召回评分的字段主要包括标题、介绍、症状、病因、主治、适用人群、功效、功能、部位、相关疾病和经络
  - 最终注入模型提示词的字段主要包括概述、相关症状、常见原因、主治、适用人群、功效、功能、配方、用法、操作、定位和归经
  - `fullText` 原始全文会保留在本地条目中，但不会整段注入模型，避免长文本带来噪声和 token 浪费
  - `就诊科室`、`来源`、`不适用人群` 等字段会保留在本地结构化数据中，但当前提示词格式没有主动输出这些字段
  - `保健品` 类仅作为参考资料，不主动向用户推荐
- 输入：
  - 主诉
  - 症状标签
  - 主题
- 技术：
  - 本地 JSON 知识索引
  - 关键词匹配和相关知识召回
- 索引与召回机制：
  - 知识库预先整理为 `entries` 和 `keywordIndex`
  - `entries` 存储 4,163 条结构化知识正文
  - `keywordIndex` 是关键词倒排索引，结构是“关键词 token -> 命中的知识条目编号列表”
  - 检索时先对查询文本做清洗，提取连续二字 token
  - 每个 token 会在 `keywordIndex` 中查找命中的知识条目
  - 命中条目会根据标题、描述、症状、主治、适用人群、功效等字段进行加权评分
  - 召回结果按类别分组，每类最多选取 3 条高分内容
  - 最终按“症状参考、相关中医疾病参考、药膳食疗参考、穴位按摩参考、保健品参考”组织成提示词参考文本
- 检索内容：
  - 症状
  - 疾病
  - 药膳食疗
  - 穴位
  - 保健品，仅作为参考，不主动推荐
- 输出：
  - 一段可注入模型提示词的 `referenceText`
- 价值：
  - 降低通用模型输出过于泛化的风险
  - 通过知识库增强调理建议的具体性，例如食疗、穴位、生活方式建议

### 3.8 综合会诊分析

综合会诊是标准结果生成链路。后端会把用户问诊信息、已完成的舌象/面象结构化观察、RAG 召回的参考知识合并到同一个提示词中，要求模型只返回四张结果卡片。返回后再经过解析和术语清洗，确保前端展示结构稳定、表达符合当前产品能力边界。

- 前端调用：
  - `src/services/tcmConsult.ts`
  - `submitFollowUp()`
- 后端 API：
  - `POST /api/tcm/analyze`
  - 文件：`src/app/api/tcm/analyze/route.ts`
- 后端输入：
  - 主诉
  - 症状标签
  - 补充问诊答案
  - 舌象/面象结构化观察结果，如果用户已完成上传和分析
  - RAG 检索结果，如果检索到相关知识
- 后端处理：
  - 使用 `buildAnalyzeUserPrompt()` 生成最终分析提示词
  - 把 RAG 召回的 `referenceText` 一起注入模型
  - 如果 `observation.tongue` 或 `observation.face` 存在，将它们作为望诊观察线索传入
  - 调用 DMXAPI/Qwen3-VL-Plus 生成分析文本
  - 使用 `parseAnalyzeResponse()` 把模型文本拆成前端卡片
  - 使用术语过滤逻辑去掉不适合当前线上问诊场景的表述
- 关键文件：
  - Prompt：`src/services/tcmPrompts.ts`
  - 结果解析：`src/services/tcmAnalyzeResponse.ts`
  - 术语过滤：`src/services/tcmTextSanitizer.ts`
- 输出：
  - 症状理解
  - 中医分析
  - 调理建议
  - 风险提示
- 价值：
  - 这是主会诊结果生成步骤
  - 把用户文本信息和知识库内容合并成可读、可展示的结构化结果

### 3.9 多模态综合分析

多模态综合分析是另一条并行分析链路。与标准综合会诊不同，它不是只使用已经结构化的舌象/面象结果，而是把主诉、补充问诊、RAG 参考和三张原始图片一起交给视觉语言模型，由模型在完整上下文中直接生成结果卡片和观察摘要。

- 触发点：
  - 用户已完成舌面、舌下、面部图片上传，并需要把文本和原始图片一起交给视觉语言模型直接综合判断
- 前端调用：
  - `analyzeMultimodalConsultation()`
- 后端 API：
  - `POST /api/tcm/analyze-multimodal`
  - 文件：`src/app/api/tcm/analyze-multimodal/route.ts`
- 后端输入：
  - `payload`：主诉、症状标签、补充问诊答案、观察状态等 JSON
  - 舌面图片
  - 舌下图片
  - 面部图片
- 后端处理：
  - 先基于主诉、症状标签、主题调用 `retrieveTcmKnowledge()` 检索 RAG
  - 把 `payload`、RAG 参考、输出 schema 和规则组成结构化文本指令
  - 把结构化文本指令、舌面图片、舌下图片、面部图片一起传给 `qwenVisionModel`
  - 返回结果后用 `parseAnalyzeResponse()` 解析四张卡片，并保留 `observationSummary`
- 技术：
  - Qwen3-VL-Plus 多图输入
  - OpenAI-compatible 多模态消息格式
- 输出：
  - Qwen3-VL 直接生成的多模态会诊结果
- 价值：
  - 与“先分别分析舌象/面象，再综合文本”的链路形成对照
  - 便于观察视觉模型在完整上下文下的表现

### 3.10 追问聊天

追问聊天用于承接用户查看结果后的进一步问题。文本追问基于已有结果卡片和历史聊天继续回答；多模态追问则基于此前生成的 `observationSummary` 和结果卡片回答，不会重新分析原始图片，保证后续对话使用的是同一份稳定观察上下文。

- 触发点：
  - 用户查看结果后继续提问
- 前端调用：
  - `continueChat()`
- 后端 API：
  - 文本追问：`POST /api/tcm/chat`
  - 多模态追问：`POST /api/tcm/chat-multimodal`
- 后端输入：
  - 用户追问
  - 已有会诊结果
  - 文本追问包含历史聊天和结果卡片
  - 多模态追问包含主诉、症状标签、补充问诊、结果卡片、历史聊天和 `observationSummary`
- 技术：
  - Chat Completions
  - 会诊上下文拼接
  - 多模态追问不会重新分析原始图片，只基于已有 `observationSummary` 和结果继续回答
- 输出：
  - 针对当前会诊结果的继续解释或建议
- 价值：
  - 支持用户围绕结果继续咨询原因、执行方式和风险边界

## 5. 后续技术规划

当前线上舌象分析仍主要依赖通用视觉模型和提示词。舌象专用模型微调已经完成验证：使用 6,719 张标注舌象图片训练 Qwen-VL LoRA，用于提升舌象分类和结构化输出的稳定性。后续重点不是“是否能训练”，而是根据产品架构判断是否把训练后的模型接入线上主流程。

舌象专用模型已经完成本地 A100 + LLaMA-Factory 微调，并产出 LoRA 模型，可用于后续舌象结构化识别验证。但考虑到当前产品仍处于 MVP 阶段，线上部署需要保持架构干净、成本可控、服务稳定，因此训练后的模型不一定直接接入生产主流程。现阶段可以继续使用通用视觉模型完成舌象分析，同时把微调模型作为后续能力储备。

如果未来决定接入舌象专用模型，产品上仍保留舌面 + 舌下双图输入。即使训练数据主要覆盖舌面标注，舌下图片上传和 `sublingualVessels` 观察字段仍作为当前产品能力保留。

移动端拍照体验优化：

1. 在手机端调起相机时增加拍摄蒙版，用框线提示舌面、舌下和面部照片的推荐位置
2. 对舌象拍摄增加“舌头伸出范围、舌面居中、避免遮挡、不要过度用力”的视觉提示
3. 对面象拍摄增加“正脸居中、面部完整、避免强逆光和过暗环境”的提示
4. 增加光线质量提醒，例如画面过暗、过曝、模糊时提示用户重新拍摄
5. 在上传前继续保留图片压缩和格式校验，降低移动端上传失败和 API 超时风险
6. 目标是提高输入图片质量，从源头减少视觉模型误判，而不是只依赖后端提示词修正

## 6. 用户使用路径

### 适用场景

适用于用户快速整理自身症状、补充关键问诊信息，并获得中医健康管理方向的参考建议。系统定位为健康咨询辅助工具，不替代线下医生诊断和治疗。

### 使用步骤

1. 打开网站
   - 进入 `https://itwins-tcm.vercel.app`

2. 输入主诉
   - 用一句话描述最困扰的问题
   - 例如：最近入睡困难、胃胀、容易疲惫、口干等

3. 选择症状标签
   - 根据页面提示选择自己符合的症状
   - 如果没有完全匹配，可以选择“其他”并补充说明

4. 回答补充问诊
   - 系统会根据主诉生成若干补充问诊问题
   - 例如睡眠、饮食、大小便、冷热感、情绪等

5. 上传舌象和面象
   - 舌象需要舌面和舌下两张照片
   - 面象上传一张清晰正脸照片
   - 尽量在自然光下拍摄，避免滤镜、美颜和过暗环境

6. 查看分析结果
   - 系统会生成症状理解、中医分析、调理建议和风险提示
   - 用户可基于结果继续发起追问

### 使用边界

- 结果仅供健康管理和调理参考，不作为疾病诊断结论
- 如果出现胸痛、呼吸困难、严重腹痛、持续高热、明显出血、意识异常等情况，应及时就医
- 图片越清晰，分析越稳定
- 主诉越具体，补充问诊和最终建议越有针对性
